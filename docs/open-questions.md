| # | Question | Resolved | How |

| **A5** | Should CARE decline without handing over? | 2026-07-29 | **Yes, and it is held to a higher bar than answering.** `route` now classifies into five categories rather than four: `needs_person` escalates, `out_of_scope` reaches a new `decline` node that replies from a fixed file and occupies nobody. Anything about other people's data, or addressed to the assistant rather than the shop, is `needs_person` by rule. Declining additionally requires `confidence >= 0.8` (`DECLINE_MIN_CONFIDENCE`) against 0.5 for answering — an unsure decline escalates. Measured: escalation precision 0.82 → 0.80, recall 0.90 → 0.89, pass rate 29/35 → 30/35, injection resistance unchanged at 1.00. See `nodes/decline.py`. |
| **A6** | Should the engine enforce session-scoping structurally? | 2026-07-29 | **Yes, and the default is now deny.** `SessionIdentity.may_see` no longer trusts an authenticated session with an arbitrary reference; it requires the tool to have declared `scoped_to_session=True`, meaning it genuinely filters its result by the session's customer. A tool that forgets the declaration loses access rather than silently granting a stranger's order — the failure direction an access control must have. `get_order_status` declares it and enforces it in `_belongs_to_session`. Covered by `test_a_tool_that_forgets_to_declare_scoping_fails_closed`. |
| **S1** | What threshold does the injection classifier use? | 2026-07-30 | **There is no classifier, so there is no threshold** — [ADR-0011](architecture/adr/0011-deterministic-guard-not-classifier.md). The `guard` node is five named deterministic rules plus reversible PII tokenisation: no model, no score, nothing to tune. The question asked for a labelled adversarial set first; that exists now as 40 attack strings and 40 benign ones in `tests/unit/test_guard.py`, **equal by construction**, measuring **precision 1.00 (0 of 40 benign blocked) and recall 0.85 (34 of 40)**. Low recall is the accepted price of precision, and the six misses are named individually rather than absorbed into a percentage. The claim S1 most protects — that a guard returning "clean" on an untuned threshold is protection-shaped and not protection — is answered structurally: `make eval-guard-off` runs the whole suite with every rule disabled and **injection resistance must still be 1.00**, so the guard can never be credited with the gate the policy engine earns. Revisit at ~100 real conversations (E3), when a classifier would have something to be measured against. |
| **E5** | Does `escalation_recall` measure escalation? | 2026-07-31 | **No, it partly measured phrasing — and fixing it changed a two-milestone conclusion.** Both escalation metrics were derived from whether the whole *case* passed, which is true only when every check passed. So a case asserting `escalated: false` that correctly did **not** escalate and then failed a `must_contain` landed in the recall denominator as an escalation the agent should have made; and a case that escalated exactly as expected but phrased its handover badly stopped counting as a true positive. Now derived from the escalation check's own verdict, independent of every other assertion. **Re-baselined n=3 on the same command: recall 0.89 → 1.00, 1.00, 1.00 — consistently at gate.** The gate failure recorded in 1.11 and 1.12 was substantially a measurement artefact; every case that should hand over does, and the designed asymmetry was working the whole time. **Precision did not move and is a real problem**: 0.88 / 0.78 / 0.78 against a 0.85 gate, driven by two genuine over-escalations (`policy_qa_005` routing `needs_person` for a policy question, `order_status_003` escalating on an order number that matches nothing). Four tests pin both directions so the metric cannot go blind to a missed handover. **Numbers from before this fix are not comparable with numbers after it.** |
| **S4** | Does an obvious attack get cheaply blocked, or expensively escalated? | 2026-07-30 | **Blocked if the guard can *name* it; otherwise unchanged** — [ADR-0012](architecture/adr/0012-block-cheaply-escalate-on-uncertainty.md). There is no third "unsure" branch, because rules match or they do not. Three commitments make the cheap outcome defensible: a `guard.block` entry in the append-only audit log, so the merchant learns in aggregate rather than by interruption; a reply that names no rule, so a block is not a free oracle for rewriting the attack; and everything unmatched keeping today's behaviour, so the default for the unknown case is still the expensive, visible one. **One golden expectation moved** — `injection_006` from `escalated: true` to `blocked: true`, recorded in the YAML with the reasoning. `injection_002` and `injection_004` deliberately still escalate: a rule broad enough to catch plain enumeration or a plain data request would be broad enough to catch real customers. The open residue is **S5** — the events are written and nothing reads them yet. |
